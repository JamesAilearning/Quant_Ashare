# 指数成分历史：截断修复与旧数据重建

## 这次代码修复了什么

`index_weight` 改为按月、串行抓取，再按指数整体写入 parquet。
CSI800 一年约有 9,600 条月度成分记录，原来一次请求整年可能只拿到后面的
7,000 条。[Tushare 官方说明](https://tushare.pro/document/2?doc_id=96)
也建议用每月首日、末日作为查询边界。

单次响应达到 6,000 条时，现在会记录 `unusable_response` 缺口，保留该指数
原文件，不发布已抓到的部分月份。6,000 是保守警戒线，不是声称接口在所有
账户下都有固定的同一个上限；未触及警戒线也不等于逐股完整性已获证明。

**合并代码不等于历史数据已经修复。** 已有文件仍然会被断点续传跳过，
`--refresh-current` 不刷新指数成分，`--reset-manifest` 也不会删除或重抓已有
指数文件。不要靠删除生产清单来“修复”历史。

已有指数文件因缺口被强制重试时，还受[汇总文件范围保护](aggregate-update-safety.md)
约束：请求须覆盖原清单范围，缺少可信范围记录则停止并保留文件。

## 第一步：只在新目录抓取候选历史

先确认当前代码包含这次修复，使用系统的标准 Python 环境；认证信息仅通过
既有 `TUSHARE_TOKEN` 环境变量传入，不写在命令、文档或日志里。

以下为 PowerShell 示例，从仓库根目录运行。选择一个**不存在的新目录**，
并根据旧清单和文件最早日期设置全量范围；不能只抓最近一个月覆盖多年文件。
示例日期只是本次审计时点，不应原样用于以后月份。

```powershell
& D:/stock/_canonical_venv/Scripts/python.exe scripts/data_pipeline/01_fetch_tushare.py `
  --output-dir D:/qlib_data/index_weight_repair_20260905_candidate `
  --endpoints index_weight `
  --indices 000300.SH,000905.SH,000906.SH `
  --start-date 20000101 --end-date 20260904 `
  --rate-limit-sleep-ms 250
```

此命令仅抓指数成分，不抓全部股票行情，不构建 provider，不改变生产模型。
避免与日常更新并发，保留调用限速。退出码非零或清单包含 holes 时禁止发布；
正常重跑同一候选目录可以重试已记录缺口的指数。

## 第二步：检查候选数据，不能只看退出码

逐个指数对比旧文件与候选文件，保留检查结果：

- 清单范围是否覆盖所需完整历史，是否有缺口，文件能否正常读取。
- `index_code` 是否与文件相符，日期是否在请求范围，
  `(index_code, trade_date, con_code)` 是否唯一；权重是否有限、非负。
- 每个快照日期的成分数量、权重合计，以及每年的快照分布。特别核对旧数据中
  缺失的月份和半截快照。不要把“每年正好 7,000 条”当正常完成。
- 指数成立前或当月尚未公布可能没有快照；不能凭空补造月份或成分。
- 不要强制历史每期恰好 300／500／800 只。数量变动和权重合计异常应与原始
  来源核对；不能归一化、补零或删行把异常伪装成通过。

本次自动化测试模拟接口截断，不会访问真实 Tushare，也不替代上述数据验收。

## 第三步：另行安排可回退的生产切换

本修复不自动执行切换。切换前应明确生产 raw/provider 路径与代码版本，并
确保无每日更新、构建或荐股任务正在读取/写入它们。保留完整的旧指数文件、
生产清单及 provider 备份，再制定同一维护窗口内的替换和重建步骤。

**不能把候选目录的清单直接覆盖生产清单**：候选清单只知道指数成分，无法
代表行情、复权、停牌等其他端点。生产清单须按现有合并规则保留其他端点的
覆盖和缺口；在明确切换方案前不要手工改写它。

重新构建和验证 provider 后，核验修复月份的历史股票池。仅复制 raw parquet
不会更新现有 provider 的 instruments。若验收失败，恢复同一备份版本的
raw、清单与 provider，不要保留相互不匹配的组合。

旧模型、旧回测报告必须保留原始数据来源；不能因为替换了历史股票池，就把
旧成绩改称“修复后成绩”。新的对照评估仍须走唯一的 qlib 正式路径，训练、
回测和生产模型替换作为后续独立任务串行执行。
