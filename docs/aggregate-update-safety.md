# 汇总文件更新：保留原有历史范围

本保护针对更名记录 `namechange`、停复牌记录 `suspend_d`、指数成分
`index_weight` 和交易日历 `trade_cal`。这些端点一次替换整个文件，不能
把“只抓最近一个月”当成给多年文件追加一个月。

## 更新被拦截时怎么办

已有文件被选中刷新或重试时，程序先读取同目录的 `fetch_manifest.json`，
包括其中仍有缺口的端点记录，再检查请求是否包含原来声明的完整范围。
若缩短任一端，会保留原文件、不发送该文件的数据请求，并记录
`unsafe_overwrite`、`attempts=0`。这不是更新成功，也不是接口调用失败。

正常完成但有缺口时，命令退出码为 `3`；若随后触发现有清单合并的范围限制，
则可能退出 `1` 并保留原清单。其他可安全处理的文件可以继续，整个任务不是
全有或全无的事务。

1. 查看错误中列出的请求范围和原覆盖范围；对重要目录先保留完整备份。
2. 使用覆盖旧范围及所需新日期的请求重试，不能只覆盖日志中的一个端点而
   忽略其他端点或更早的未解决缺口。程序不会自动扩大下载范围或合并新旧行。
3. 核对退出码、清单缺口和实际文件后再使用数据。非零退出不能继续当成
   成功更新。`--refresh-current` 仍不刷新已有指数文件；指数缺口强制重试
   仍使用 `index={code}`，其他三个端点使用 `file` 作为稳定单位。

交易日历实际始终从 `19901201` 请求，不使用用户指定的较晚起点。
旧清单可能记了比交易所历史还早的用户起点，比较时也按这个实际起点截取；
日历结束日期仍不得倒退。

## 没有可信清单，不能靠重试“变可信”

已有文件（包括空文件）缺少可用的原覆盖记录时，程序会在该文件的请求前
明确终止，命令退出 `1`，不生成这次运行的新清单。原因是：如果只写一个
普通缺口，下一次运行可能把它记录的狭窄日期误当成旧文件的完整来源范围。

适用检查为所消费的 schema 版本、端点状态和真实、有序的八位日期，以及
既有读取器报告的清单损坏。它不是对清单所有其他字段的新一轮完整校验。

不要编造日期、删除旧文件或用 `--reset-manifest` 绕过保护。这个参数只删除
清单，不删除原始数据；旧文件仍然没有可用于覆盖的可信记录。应保留并检查
原文件与清单，在**另一个空的暂存目录**重新获取所需完整范围，验收之后再
单独安排可回退的生产切换。[指数历史重建说明](index-weight-history-repair.md)
提供了分阶段处理方法，本次代码不执行生产数据修复。

## 保持不变及不能保证的部分

- 首次写入不存在的目标文件、只跳过不写入的续跑，以及 dry-run 保持原行为。
  直接调用 Fetcher 的脚本若要覆盖已有文件，也必须有真实的原清单证据。
- `stock_basic` 是完整股票快照，不按查询日期截取，保持独立刷新语义。
  每股每年文件仍使用[原有覆盖保护](ticker-year-update-safety.md)。
- 清单是端点级范围记录，不是与每个文件字节绑定的来源证明。手工复制的
  文件、以前已经不准确的清单、接口响应内部缺失，不能靠此检查自动发现或修复。
- 不新增正式指标，不改变模型、选股或 qlib 计算路径，不支持同目录并发写入。
