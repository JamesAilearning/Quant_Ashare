# 汇总文件更新：保留原有历史范围

本保护针对更名记录 `namechange`、停复牌记录 `suspend_d`、指数成分
`index_weight` 和交易日历 `trade_cal`。这些端点一次替换整个文件，不能
把“只抓最近一个月”当成给多年文件追加一个月。

## 更新被拦截时怎么办

已有文件被选中刷新或重试时，程序先读取同目录的 `fetch_manifest.json`，
包括其中仍有缺口的端点记录，再检查请求是否包含原来声明的完整范围。
若缩短任一端，会保留原文件、不发送该文件的数据请求，并记录
`unsafe_overwrite`、`attempts=0`。这不是更新成功，也不是接口调用失败。

正常完成但有缺口时，命令退出码为 `3`；若随后触发现有清单合并的范围限制，
则可能退出 `1` 并保留原清单。其他可安全处理的文件可以继续，整个任务不是
全有或全无的事务。

1. 查看错误中列出的请求范围和原覆盖范围；对重要目录先保留完整备份。
2. 使用覆盖旧范围及所需新日期的请求重试，不能只覆盖日志中的一个端点而
   忽略其他端点或更早的未解决缺口。程序不会自动扩大下载范围或合并新旧行。
3. 核对退出码、清单缺口和实际文件后再使用数据。非零退出不能继续当成
   成功更新。`--refresh-current` 仍不刷新已有指数文件；指数缺口强制重试
   仍使用 `index={code}`，其他三个端点使用 `file` 作为稳定单位。

交易日历实际始终从 `19901201` 请求，不使用用户指定的较晚起点。
旧清单可能记了比交易所历史还早的用户起点，比较时也按这个实际起点截取；
日历结束日期仍不得倒退。

## 汇总历史比行情更早时，显式指定各自起点

`01_fetch_tushare.py` 和 `daily_update.py` 支持三个可选参数：

- `--namechange-start-date YYYYMMDD`
- `--suspend-d-start-date YYYYMMDD`
- `--index-weight-start-date YYYYMMDD`

不传时仍使用原来的 `--start-date`；不从旧清单自动扩大请求。传入时只改变
该汇总端点的请求和清单覆盖起点，不改变 `daily`、`adj_factor`、`daily_basic`
或基准行情范围，所有端点继续使用同一个 `--end-date`。例如已核对改名、停牌、
指数分别有1990、2015、2000年起的历史，而行情日更从2018年开始，应分别传入
对应起点，不能把共同起点直接改为1990年。日期须为真实的八位ASCII数字且不晚于
结束日期；无效新参数在清单重置、客户端构造和日更状态写入之前拒绝。

这不是保护豁免：指定的起点仍然太晚、结束日期倒退、旧来源未知时照样拒绝。
指数参数也不强制刷新已有文件；无缺口的指数仍跳过，清单不会因为传了较早起点
就冒称已重新获取历史。实际文件仍需按[历史修复说明](index-weight-history-repair.md)
在隔离目录验收，再安排成套切换。

库调用者使用 `TushareFetcherConfig` 的同名可选字段。若自行持久化结果，必须把
`config.aggregate_start_dates()` 同源传给
`build_manifest(..., endpoint_start_dates=config.aggregate_start_dates())`；结果DTO
本身不携带请求日期。省略映射保留旧的共同范围接口含义，并不会自动读取Fetcher配置。
清单JSON仍是schema v1，非本次运行的端点和盲跳过的覆盖处理不变。

指数清单是整个端点的共同覆盖，不是逐指数覆盖。若部分指数需要重试、部分旧文件
保留（包括目录内未被 `--indices` 选中的文件），请求的起止必须与可信旧共同范围
完全一致，且每个旧缺口都要实际重试。这样的同范围保留才计为 `units_verified`，
它表示沿用已知范围，不是新API响应或逐文件内容认证。扩大或缩小范围的混合更新
会在该端点第一个数据请求前拒绝；不得把只补齐一个指数说成所有指数都补齐。
全跳过仍不建立新范围；重复指数参数拒绝，不隐式去重。要扩大共同历史，请在独立
空目录抓齐所需指数并按历史修复流程验收，不能靠重置清单或隐式强刷旧文件。

## 没有可信清单，不能靠重试“变可信”

已有文件（包括空文件）缺少可用的原覆盖记录时，程序会在该文件的请求前
明确终止，命令退出 `1`，不生成这次运行的新清单。原因是：如果只写一个
普通缺口，下一次运行可能把它记录的狭窄日期误当成旧文件的完整来源范围。

适用检查为所消费的 schema 版本、端点状态和真实、有序的八位日期，以及
既有读取器报告的清单损坏。它不是对清单所有其他字段的新一轮完整校验。

不要编造日期、删除旧文件或用 `--reset-manifest` 绕过保护。这个参数只删除
清单，不删除原始数据；旧文件仍然没有可用于覆盖的可信记录。应保留并检查
原文件与清单，在**另一个空的暂存目录**重新获取所需完整范围，验收之后再
单独安排可回退的生产切换。[指数历史重建说明](index-weight-history-repair.md)
提供了分阶段处理方法，本次代码不执行生产数据修复。

## 请求范围足够宽，响应仍可能不完整

`namechange`、`suspend_d` 现在还会检查实际候选记录。曾出现扩大请求后，
停复牌文件仍是 5,000 行，但原来的 2018 年记录被另一批 2015 年记录全部
替换的情况；行数相同、范围声明正确、文件原子写入，都不能证明业务历史保住了。

- 停复牌按日历月顺序请求，首尾严格裁到指定范围。原始返回达到 5,000 行时
  将该段二分，直到低于警戒线；单日仍达到警戒线就拒绝。先检查原始行数，
  再去除完全重复的行；分段后的结果不能丢掉父查询已经返回的记录。
- 更名返回达到 10,000 行时拒绝覆盖，不自动切换分页或日期分段。这两个
  数字是实际异常暴露出的保守警戒线，不是 Tushare 永远不变的接口上限。
- 只有所有请求和检查成功，才一次写入文件。字段/日期异常、旧业务键缺失
  或预算用尽等响应检查失败，都保留旧文件并记录 `unusable_response` 的
  `file` 缺口；重试耗尽仍保留原来的网络错误分类。鉴权、参数错误和旧
  Parquet 不可读仍直接终止，不当成普通响应缺口。零写入不推进旧清单覆盖。
- 停复牌保护四个原字段；更名保护除 `end_date` 外的五个原字段，只允许其余
  字段完全相同记录的结束日期修正。同日不同名称分别保留；同一键对应冲突
  结束日期会拒绝，不擅自取最后一条，也不把旧行拼入不完整的新结果。
- 单端点最多 2,000 个分段请求，每次仍使用现有有界重试和限速；候选最多
  1,000,000 行、256 MiB DataFrame 深内存。超过预算会明确失败，不截取结果。
  这是采集预算，不是整个 Python 进程的峰值内存承诺。

更名的 `start_date/end_date` **查询参数**按[官方说明](https://tushare.pro/document/2?doc_id=100)
指公告日期，而输出中的 `start_date` 是生效日期，不能混用。返回的缺失公告
日期保持缺失，不能用生效日期补上。官方仓库有用户报告指出日期查询可能
漏掉无公告日期的历史，分页也可能遗漏全局记录（[#1858](https://github.com/waditu/tushare/issues/1858)、
[#1901](https://github.com/waditu/tushare/issues/1901)）；这些是风险线索，
不是官方确认的当前账户行为。**本次防丢失保护不等于更名全历史已经补全。**

看到此类缺口时，先保存新旧文件、清单和日志，保持生产验收暂停。不要删除
文件、重置清单、盲目重跑或绕过缺口；在独立目录验证源查询和旧记录保留后，
再单独安排生产发布。代码合并不自动恢复定时任务。

## 显式重建逐股票更名历史

`01_fetch_tushare.py` 和 `daily_update.py` 支持
`--namechange-mode per_security_full`。默认仍为 `date_range`，不会在失败后
自动切换。这只改变更名采集方式，不改变模型、选股或停复牌采集。

新方式按“当前上市快照 + 退市快照 + 原更名文件出现过的代码”的并集逐只
请求，查询不带公告日期条件。返回历史原样保留，包括范围外的有效记录和
缺失公告日期；不会用生效日期补公告日期，也不会把旧行拼进新结果。
每份响应必须属于当前请求的股票，所有请求完成并保留旧业务键后才一次落盘。

两份股票快照都必须包含采集端请求的全部字段（包括名称、上市日、退市日），
不能只保留代码等选取字段。快照必须非空、完整、无缺口、代码和状态有效，且内嵌快照日期与本次运行
日期一致；可在同次采集中明确刷新 `stock_basic`，不能依赖文件存在来掩盖
刷新失败。已有更名文件必须显式刷新或重试已记录的文件缺口；新方式不把
旧文件的盲跳过称作完成重建。`--dry-run` 仍不调用接口、不写文件。

代码通常为六位数字加 SH/SZ/BJ。隔离恢复中，在两代退市来源都确认的
`T600018.SH` 是唯一明确支持的历史例外：只允许在退市快照和历史更名上下文
出现，上市快照仍拒绝。它与 `600018.SH` 是不同标识，查询、保留检查和输出
都保留原样，不删除 `T`，也不把规则推广到其他 T 前缀代码。新遇到的未知
标识仍应保留失败证据并单独核实，不能跳过记录来完成恢复。

这一例外不授权日行情、复权因子或每日指标接口查询。在新方式下，这三个
入口也检查完整同日股票快照。只有能证明请求区间完全在该历史证券上市期
之外、没有待重试缺口、涉及年度的已有文件均可读且为空时，才警告后排除
该标识，不新建空文件、不增加写入或验证计数。日期缺失、区间相交、旧文件
非空或损坏、以及待处理缺口都会明确失败。普通 `600018.SH` 不受此排除影响。
这不是对同次运行已完成的聚合写入进行回滚，也不会改变默认旧模式。

新方式下，股票快照先暂存两桶响应并联合检查，再写入文件。接口或校验失败时，
两份旧快照都保留，清单在 `stock_basic` 记录两桶缺口，不能写成“快照刷新完成”。
跳过的旧快照若参与检查，仍不算本次新刷新。这里的落盘是逐文件原子写，不是
跨两文件事务；磁盘写入异常会直接失败，不能把这类失败称为完整刷新成功。

例如在**独立恢复副本**中选择 `--endpoints stock_basic,namechange,suspend_d`、
`--refresh-current` 和上述新方式，同时显式保留原来的各端点起点及所需截止日。
不得重置清单来绕过旧范围保护。全部证券最多 10,000 只，每只响应低于
10,000 行，并保留累计行数、内存和限速保护；预算不足会失败，不截取成功。

清单日期仍是本次声明的作业范围，不是输出记录的最早/最晚日期，也不是
“所有股票的全部历史均已验证”证明。逐股票返回的未曾观察记录仍需独立验收。
生产切换前应分别对比原暂存历史与当前生产历史，保存请求清单、空响应、
记录统计和文件摘要，再验证 provider 及荐股工作流。生产定时入口也须显式
配置新方式；仅代码合并不会恢复任务或修复已经丢失的数据。

## 仍然保留的限制

- 默认日期模式只跳过不写入的续跑，以及所有 dry-run 保持原行为；两种聚合文件首次写入也必须
  通过新的响应检查，不能把初次创建的截断文件当成成功。
  直接调用 Fetcher 的脚本若要覆盖已有文件，也必须有真实的原清单证据。
- `stock_basic` 是完整股票快照，不按查询日期截取，保持独立刷新语义。
  每股每年文件仍使用[原有覆盖保护](ticker-year-update-safety.md)。
- 清单是端点级范围记录，不是与每个文件字节绑定的来源证明。手工复制的
  文件、以前已经不准确的清单、从未返回过的内部缺失，不能靠此检查自动发现或修复。
- 不新增正式指标，不改变模型、选股或 qlib 计算路径，不支持同目录并发写入。
