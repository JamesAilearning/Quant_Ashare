# CI 装的每一条依赖都要有上界

## Why

2026-08-22，PR #462 的 CI 六腿全红，而当天的改动与失败点无关。

`pyproject.toml` 写的是 `pytest>=7.4`，没有上界，CI 每次装最新——那天装到的是刚
发布的 **9.1.1**，本机共享 venv 停在 **9.0.3**。9.1 的 logging 插件行为变化让一条
测试判红，而 9.0.3 不会。于是本机全绿、CI 全红，排查花掉一整轮。

这不是那条测试的偶然。**工具链在判代码**：pytest 跑测试、mypy 查类型、ruff 挑
lint。它们任何一个漂移，红的就不是代码，而是当天的运气。而运行时依赖
（numpy / scipy / pandas）**早就有上界了**，正是因为它们此前咬过人——同一个道理
没有推广到判代码的那一半。

## What Changes

- `dev` 组四条（pytest / pytest-cov / ruff / mypy）加**下一个小版本**上界，下界
  同时抬到 CI 实际使用的那个小版本，让「本机装的」与「CI 装的」是同一个。
- `ui` 组三条与 base 依赖里那六条（pyarrow / ruamel.yaml / PyYAML / matplotlib /
  optuna / python-dateutil）加**大版本**上界——`pip install -e ".[dev,ui]"` 会把
  base 依赖一并解析安装，只管 extra 等于漏掉一半。
- 守卫：CI 装的每一条依赖都必须有上界；覆盖面（base + 哪些 extra）从 workflow
  的安装行推导，不手抄组名表。
- 顺带补一条：pyproject 的 numpy / scipy 窗口在 workflow 里被又抄了一遍（因为
  qlib 要在项目安装之前先装，拿不到 pyproject 的约束）。抄是必要的，零一致性
  测试不是——而且**不止一处**：`test.yml` 与 `regen-baseline.yml` 各抄了一份，
  后者正是产出 REGEN-2 确定性锚的那条路径。守卫因此扫遍全部 workflow。

## 为什么两种粒度不一样

**判代码的工具**给**下一个小版本**上界：新检查与新行为多在小版本引入，补丁版
按各家政策只修 bug。打破 #462 的正是一次小版本跳变（9.0 → 9.1），`<10` 那种大
版本上界对它毫无作用；而只要求「上界带两段数字」也不够——`<10.0` 是一个穿着小
版本外衣的大版本上界，所以要求上界正好等于下界的下一个小版本。

`pytest-cov` 算在判代码的工具里：它是 pytest 插件，挂进同一次运行，小版本变化
同样能改变判定。

**被代码使用的库**给大版本上界：破坏性大版本要挡住；小版本变化打破了 UI 测试，
那是真实的兼容性信号，值得红一次让人看见，不该被上界闷掉。

## Non-goals

- 不引入 lockfile / constraints 文件。上界挡不住补丁版漂移；要做到完全确定性得
  上锁文件，那是更大的一步。

## 首版把 base 依赖排除在外，那是错的

首版把 `dependencies` 里那六条列为 Non-goal，理由是「收紧运行时依赖会与 qlib
的约束在解析期相互作用」。但规范正文写的是「CI 装的**每一条**依赖都要有上界」，
而 `pip install -e ".[dev,ui]"` 明明会把 base 依赖一并解析——**规格与实现直接
矛盾，且守卫全绿**（codex P1）。

正确的做法不是把规范改窄，而是把规则**照它自己说的**应用完：这六条是被代码
使用的库，按已经写下的分类给大版本上界。取值都在 CI 实测版本之上（pyarrow
25.0.1 · ruamel.yaml 0.19.1 · PyYAML 6.0.3 · matplotlib 3.11.1 · optuna 4.9.0 ·
python-dateutil 2.9.0），对当前解析结果是无操作。
