# CI 装的每一条依赖都要有上界

## Why

2026-08-22，PR #462 的 CI 六腿全红，而当天的改动与失败点无关。

`pyproject.toml` 写的是 `pytest>=7.4`，没有上界，CI 每次装最新——那天装到的是刚
发布的 **9.1.1**，本机共享 venv 停在 **9.0.3**。9.1 的 logging 插件行为变化让一条
测试判红，而 9.0.3 不会。于是本机全绿、CI 全红，排查花掉一整轮。

这不是那条测试的偶然。**工具链在判代码**：pytest 跑测试、mypy 查类型、ruff 挑
lint。它们任何一个漂移，红的就不是代码，而是当天的运气。而运行时依赖
（numpy / scipy / pandas）**早就有上界了**，正是因为它们此前咬过人——同一个道理
没有推广到判代码的那一半。

## What Changes

- `dev` 组四条（pytest / pytest-cov / ruff / mypy）加**小版本**上界，下界同时抬到
  CI 实际使用的那个小版本，让「本机装的」与「CI 装的」是同一个。
- `ui` 组三条（streamlit / plotly / reportlab）加**大版本**上界。
- 守卫：CI 装的每一条依赖都必须有上界；覆盖面从 workflow 的安装行推导，不手抄
  组名表。
- 顺带补一条：pyproject 的 numpy / scipy 窗口在 workflow 里被又抄了一遍（因为
  qlib 要在项目安装之前先装，拿不到 pyproject 的约束）。抄是必要的，零一致性
  测试不是。

## 为什么两种粒度不一样

**判代码的工具**给小版本上界：新检查与新行为多在小版本引入，补丁版按各家政策
只修 bug。打破 #462 的正是一次小版本跳变（9.0 → 9.1），`<10` 那种大版本上界对
它毫无作用。

**被代码使用的库**给大版本上界：破坏性大版本要挡住；小版本变化打破了 UI 测试，
那是真实的兼容性信号，值得红一次让人看见，不该被上界闷掉。

## Non-goals

- **不动 `dependencies` 里那六条无上界的运行时依赖**（pyarrow / ruamel.yaml /
  PyYAML / matplotlib / optuna / python-dateutil）。它们同样会漂移，但收紧运行时
  依赖会与 qlib 自己的约束在解析期相互作用，风险与本次要解决的问题不成比例。
  留作单独一次裁决。
- 不引入 lockfile / constraints 文件。上界挡不住补丁版漂移；要做到完全确定性得
  上锁文件，那是更大的一步。
