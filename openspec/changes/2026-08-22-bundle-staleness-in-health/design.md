# Design: 把「距出单下限还剩几天」变成一等公民

## 为什么不是「再加一个阈值」

诱惑是给健康加一条 "超过 N 天就变黄"。那只是又一个要有人去调的旋钮，而且
和真正决定成败的那个数（出单闸）没有必然关系。

本 change 只承认**一个**来自别处的事实：

```
RecommendationConfig.bundle_max_age_days = 14
```

于是唯一要算的量是

```
days_until_stale_floor = 14 - (今天 - bundle 末日).days
```

它是**剩余预算**，不是我发明的分级线。展示它，比展示任何颜色都有信息量。

## 状态如何降级

只有一处降级是**无阈值**的、纯事实的：

| 剩余天数 | 状态 | 依据 |
|---|---|---|
| `<= 0` | `error` | 出单**此刻**就会被 `_assert_bundle_fresh` 拒掉 |
| `> 0` | 沿用既有的结构判定（ok / warning） | 结构没问题，预算也没用完 |

没有中间的黄色阈值。要提前示警，交给队列（见下）——把「颜色」和「待办严重度」
分开，是因为前者描述数据包本身，后者描述**操作人现在要不要动手**。

## 队列升级：为什么是「用掉一半预算」

`update:failed` 现在恒为 `attention`。三晚故障说明：一个只会说「注意」的条目，
在预算被吃掉一半时仍然只说「注意」。

升级规则取

```
剩余天数 <= 下限的一半（14 // 2 = 7）  =>  blocker
```

理由是**对称**且可解释的：**你已经烧掉一半预算，剩下的时间不比已经损失的多。**
这不是从经验里挑的数，是从下限本身推出来的，下限一改它自动跟着改。

它是一条**策略**，所以写成具名常量并把理由写在代码里；将来要改，改的是这条
被命名的策略，不是散落各处的魔法数字。

## 下限值从哪来：沿用 #454 的惯例，不新发明

`daily_recommend` 绑定 qlib，读侧 UI 不能导入它（会把整个 qlib + gym 拉进
Streamlit 进程）。#454 已经为 `artifact_schema_version` 立过惯例：

> UI 侧钉一个具名常量，用一条测试**读生产者源码做字面对齐**。

照抄这一条：UI 侧 `BUNDLE_MAX_AGE_DAYS = 14`，测试断言
`"bundle_max_age_days: int = 14"` 出现在 `src/inference/daily_recommend.py`
的源码里。生产者改成 15 而 UI 没跟，测试立刻红。

## 「今天」必须可注入

比较涉及当前日期。默认取**东八区**的今天——bundle 的末日是 A 股交易日，用 UTC
会在午夜前后差一天；`daily_recommend` 已经为同一理由固定了 `_CN_TZ`。

所有计算函数接受可选的 `today`，测试传定值，不依赖机器时钟。

## 不做

- 不引入交易日历来判断「是否落后一个交易日」。UI 的健康判定是渲染路径，
  不该为此再依赖一份日历数据；剩余预算这个数已经足够回答操作人的问题。
- 不改出单侧的闸值，也不改任何运行时语义。
