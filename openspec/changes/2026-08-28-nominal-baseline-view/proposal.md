# 名义持仓基准：我此刻跟的是哪一天的那张单

## Why

生产是 csi800 / N5 / **周频 iso_week**。绝大多数交易日是 HOLD 日，出单工件写
`rebalance_day: false`，页面顶部挂一条「本工件为监控视图，不构成入场指令」的
红色横幅。

于是「我此刻名义上该持有什么」这个问题，答案**通常不是今天这一页**——它在
最近一个再平衡日的那张单上。而这一页此前只能一次看一天：日期下拉框只给日期、
**不标哪天是再平衡日**，要找到那一天得逐个日期点开、逐个看那条横幅。全仓也
没有任何函数向后扫描找「最近一个 `rebalance_day: true` 的工件」。

本机实测就是这个状态：磁盘上两份工件，最新的 `2026-07-31` 是 HOLD 日，更早的
`2026-06-16` 是 v1（schema 不受支持）——**当前没有可信的名义持仓基准**。这是
一个治理事实，而操作人今天完全看不见它。

## What Changes

一段**只读对照**：在候选表之前，回答「截至所选日期，名义上跟的是哪一天的那张
单、那张单上有哪些代码」。

**回溯是一次可复核的搜索**，不是一个静默的查找：

- 找到了 → 说是哪一天、多少只、`topk` / `universe`，并列出代码；
- 没找到 → 说清**已回溯几份**，并逐条列出沿途每一份工件**各自因为什么**被
  跳过（HOLD 日 / 没有节奏字段 / 节奏字段形状违约 / schema 不受支持 / 建仓
  时点不合法 / 读不出来）。

「基准在 30 天前」与「一份合格的基准都没有」对操作人的下一步完全不同；中途
被 HOLD 日填满，还是被一串损坏工件填满，也不同。所以不合并成一句「不可用」。

**不推断缺失**：老工件没有 `rebalance_day` 字段时**不**当作再平衡日。
`hold_state` 对它返回 `is_hold=False`（向后兼容语义），只看 `is_hold` 会把一份
根本没有节奏语义的老工件误当基准——那是替一次没记录节奏的运行编造语义。

**回溯有硬上界**（默认 60 份）并在撞上界时说出来。无上界地往回翻既慢，又会
把「基准早已过期」说成「找到了」。

## 红线（操作人明令，机器执法）

这一段是这一页第一次出现「应当持有什么」的表述，也因此是最容易往执行工具方向
滑的地方。红线钉在测试里，不靠文档提醒：

- **不接收手输持仓**：页面不得出现 `st.text_area` / `st.number_input` /
  `st.data_editor` / `st.file_uploader`；
- **不生成差分单、不设缓冲带**：执行口径的词不得出现在**渲染出去的文字**里
  （用 AST 取真正传给 `st.*` 的字符串字面量来查——这一页大量**否定**这些词，
  全文禁词会把正确的免责声明也判红）；
- **不越「一键下单只差复制粘贴」红线**：不得有 `st.download_button`、
  `execCommand`、`navigator.clipboard`；
- 明说它是只读对照，且明说**不知道**操作人的实际账户持仓。

**名单只能是代码集合**：工件里只有 `rank` / `predicted_score` /
`tradable_flag`——没有权重、没有股数、没有金额。把一个等权假设写进来，就是凭空
造出一份工件从未记录的仓位。

## Impact

- Affected specs: `v2-daily-decision-page`
- Affected code：`web/operator_ui/pages/_daily_decision_helpers.py`（纯函数
  `find_nominal_baseline` / `baseline_roster` + 分因常量）、
  `web/operator_ui/pages/daily_decision.py`（渲染）
- **只读**：不写任何工件；读盘走本页既有的 `read_json_artifact`，因此仍受
  `guard_output_path` 的输出目录守卫约束。这一页唯一的写面仍然只有决策日志
  追加。
- **不重推产出器语义**：只读产出器写下的 `rebalance_day`，绝不引入
  `src.inference.rebalance_schedule` 自己按日历算哪天该再平衡（那会跨越
  `web/` 现有的 import 边界）。
- 新增的是**向后回溯读多份工件**这一 I/O 模式（此前每次只读一份），因此设了
  扫描上界并把它呈报出来。

## 划界（本 change 不做）

- 不做基准名单 × 当日 top-K 的成员对照（那是下一个 PR，依赖本 PR 的基准定位）。
- 不做跨日的决策履历浏览（再下一个；它要能在**工件缺失**时照常工作，会打破
  「页面由工件驱动」这个现有前提，需单独设计空态）。
- 不碰决策日志的 schema 或写入路径。
