# 更新运行要留下历史，日志要说清哪一段属于哪次运行

## Why

**一、每晚的运行互相覆盖，「连败」这个事实无处可查。**

`<provider>.daily_update_status.json` 是**单文件**：每次运行写两遍（running →
finished），下一次直接盖掉。于是 UI 只看得到**最后一次**。

2026-08-17 / 08-20 / 08-21 连着三晚失败，拖到第三晚才被发现。#461 让待办队列
按出单余量升级严重度、#462 让失败原因走到操作人眼前——但**「连着三晚」这个模式
本身，至今没有任何东西记录**。余量是从 bundle 日期倒推的，而 bundle 日期只在
成功时才动，对「连败」只是间接证据。

对照：研究运行**有**编目（`output/runs/_index.jsonl`），生产运行没有。

**二、日志的归属问题，写入侧一直欠着一句话。**

`web/operator_ui/update_progress.py` 的模块文档列了**四种试过又否掉**的启发式
（按 mtime 丢弃 / 挂钟回退当边界 / 进度时刻 ≥ 起跑时刻 / 用 mtime 反推跨天），
结论是：

> 结论是**结构性的**：靠这份日志做不到精确归属。……要精确归属，得先让写入侧
> 落一个**带日期**的运行边界——那是另一个改动，不在本模块的承诺里。

**本改动就是那个改动。** 日志行只带 `HH:MM:SS` 不带日期，所以「昨天 21:00」与
「今天 21:00」在数据里完全不可区分；写入侧落一个带日期的边界之后，读侧不必再
猜。

## What Changes

- **运行台账**：每次运行在终态**追加**一行到
  `<provider>.daily_update_ledger.jsonl`。只可追加，不可覆盖。
- **运行边界**：运行开始时往日志里写一行带**完整日期时间**的边界，标明 provider
  与起跑时刻。
- **读侧**：新增台账 reader；`update_progress` 按边界切段，能确定归属时如实说
  「属于本次」，切不到边界时仍如实说「无法归属」——不猜。
- **今日工作台**：加一条「近 N 次」条带，让连败一眼可见。

## 与既有状态工件的关系

台账**不取代**状态工件，两者职责不同：状态工件回答「**这一次**怎么样」（且被
`--status-path` 允许改道、因而带一整套路径守卫），台账回答「**最近几次**是什么
形态」。

台账刻意**不提供 CLI 覆盖**：路径由 provider 名派生，**台账自己**无从被改道。
但评审指出攻击面的**另一头**仍在：别的可配置路径（--status-path /
--delisted-registry / --reference-cases / 两个可变根）可以反过来指到某个
provider 的台账上——status 的原子替换会把只可追加的历史整个截掉，swap 会把
它 rename 走。所以 `DailyUpdateConfig.__post_init__` 把
`*.daily_update_ledger.jsonl` 整个名字形状（含作为祖先目录）保留给台账写入
者，构造期拒绝，与状态工件的路径守卫同层。**这些守卫不是多余的**——「不提供
CLI 覆盖」只封住了一个方向。

## Non-goals

- **不改任何既有阶段语义。** 所有新增写入都在 `run_daily_update`（可观测性层），
  `_execute_daily_update` 一个字节不动。
- **不动 fail-loud 通道。** 台账写入沿用状态工件那条被 codex 加固过的反向耦合
  契约：可观测性失败**只**记 ERROR，绝不改变退出码。
- **不存耗时字段**。它可由 `started_at` / `finished_at` 推出；存一份冗余值只是
  多一个会与推导值分叉的地方。
- **不做进度条**。`update_progress` 拒绝百分比条的理由（fetch 只是六阶段里的
  第二个）没有变化，本改动只解决归属。
- **不改 `--status-path` 的行为**，也不给台账加同类覆盖开关。
