# 详情页看着一个还在跑的运行，却没有通往它活体状态的路

## Why

结果页读的是**产物**，而产物要跑完才齐。运行还在跑时，这一页能显示的就是一份
半成品报告；操作人真正想知道的「它现在到哪一步了、要不要停」只有作业页有——
那里有阶段进度、停止按钮、以及作业页自己的自动刷新。

现状要靠手工接力：记住/复制 run_id → 打开作业页 → 状态筛选选「运行中」→
把 id 粘进搜索框。四步里任何一步走神，看的就是另一次运行。结果页现有的
「返回作业列表」按钮反而更远：它 `st.query_params.clear()` 之后跳过去，落在
一个未筛选的全量列表上。

## What Changes

- 结果页在所选运行**仍在运行**时多一个「前往作业」入口，链接带该 run_id 与
  「运行中」筛选，一步落到那一行。
- 判定与链接形状收在一处纯函数 `web/operator_ui/jobs_jump.py`；页面只负责
  渲染。判据分两处写必然分叉——本仓在目录折叠上已经栽过一次。
- 链接带一个一次性 handoff 令牌，且**这次导航请求的每个筛选**都由该令牌一次性
  压过页面上的陈旧控件状态。作业页只在「URL 值与上次消费的 URL 值不同」时才
  覆盖既有筛选控件，而本链接请求的 `status=running` 与 `search=<run_id>` 恰恰
  都可能与操作人上次访问时留下的值相同——不带令牌会被**静默忽略**。

## 只在能看到运行中的运行的页面上给入口

滚动验证详情页**不给**这个入口，因为它在结构上看不到运行中的运行：
`JobManager.start()` 把 `run_dir` 初始化为 `None`，`job_runner.main()` 只在子
进程成功之后才写它，而那一页只列有 `run_dir` 的记录。在那里画入口，画出来的
是一条永远不触发的分支——而对着它写的测试只能捏造「运行中 + 有产物目录」这个
生产里不存在的组合，等于零覆盖。

（首版两页都接了，正是这个问题被评审抓到后撤回的。撤回的划界由一条钉住那三条
前提的测试守着：任何一条变了都该重新评估。）

## 本 change **不新造**判据、**不引入**任何轮询

「运行中」用的就是产出器写进作业记录、经 `job_io` 归一后的那个 `status` 词
（结果页判自动刷新用的同一个判定，逐字照搬，不做 strip、不扩同义词）。带过去
的每个参数都在**出发侧**先跑一遍作业页自己的 `_param_guard.sanitize`。

结果页既有的 opt-in 自动刷新原样不动；本入口是一条链接，不轮询、不重跑、不
改任何作业或产物状态。

## 作业页的一次性交接语义要跟着收一次口

本 change **会**动 `handoff_keys`：把 `search` 加进去。

不这么做的后果是这条链接的契约不成立：操作人跟着链接来过一次、改过搜索框、
再跟**同一个运行**的链接来——URL 的 search 值没变，普通路径于是保留他手打的
词，链接显示不出那一行、或者显示**另一个运行**的行，而针对「选中行」的动作
（含停止）就指向了错的运行。

扩这个集合**不会**误伤只带 status 的队列链接：那条链接的 URL 里没有 `search`，
`_qp_read` 给出默认空串，于是搜索框被一次性重置——这正是它能显示「该状态的全部
作业」所需要的。URL 是这次导航的**完整**筛选状态，令牌只负责让它压过 Streamlit
的控件粘性。

（首版在这里加过「该键在 URL 里才覆盖」的前提，想让「没带就别动」。四个真实场景
实测下来它更差：settled 态与非典型残值态下，**同一条队列链接**会给出不同行为，
取决于 `jobs_last_url_*` 这种内部残值。评审建议的「交接键没带就整段跳过重播种」
更差——队列链接会保留一个无关的搜索词，操作人看到空列表、以为那条队列项消失了。
三个变体的逐场景对照见 tasks.md。）

## Non-goals

- 不做详情页自动刷新（fragment 轮询是另一件事，风险面另计）。
- 不改作业页的筛选**值域**、`_DEFAULTS` 的内容、或任何筛选的语义。
- 不给终态运行任何入口——那里没有「活体状态」可看。
- 不改滚动验证页对运行中作业的可见性（那一页只列已完成的运行，是它自己的
  设计，本 change 只是不在那里画一个永不触发的入口）。
