# 手动更新误点后没有回头路：想取消只能等两小时或开任务管理器

## Why

自动更新已经跑完，操作人误点了「后台启动数据更新」——现在没有任何受控的
取消通道：要么陪它跑完（约两小时），要么自己开任务管理器杀进程（绕过一切
守卫、无日志归属、状态不明）。操作人要的是：取消，并且数据保持最后一次
成功更新的那份（无论自动还是手动）。

## What Changes

- 运行中心新增「取消本会话启动的手动更新」：仅当本 UI 会话持有**活的进程
  句柄**且进程仍在飞时可见；两步确认（武装 → 确认/保留）。
- `update_runner.cancel_update(process, log_path)`：取消的唯一通道是
  `Popen` 句柄（绝不按 pid 杀——pid 会被系统回收复用）；调度器的自动运行
  不是本 UI 子进程、没有句柄，天然不在射程。
- 结局如实分三态：进程已自行结束（no-op，不落取消标记）；已取消（POSIX
  礼貌信号生效=编排器自写终态 / Windows 强制终止）；取消失败（带原因）。
- 取消动作在共享日志落带日期的 `[run_center]` 标记（请求 + 结局），复用
  launch 的归属惯例。

## 数据安全不是本 change 实现的，是它敢存在的前提

管线是 build-then-atomic-swap：六阶段全程写 `<provider>.new` 旁路，只有
校验通过后的最后一步才原子切换上线。切换前任意时点终止进程，在线 bundle
一字节不动——仍是最后一次成功更新的数据。遗留半成品由下次运行的 Stage-0
启动修复清理（既有崩溃容忍机制）；单飞锁是 OS 级的，随进程消亡自动释放。

## 平台差异是实测的，不是猜的

- **POSIX**：子进程 `start_new_session=True` 是会话组长——`killpg`
  SIGINT → KeyboardInterrupt → 编排器 BaseException 终录路径（#465）：
  状态工件与台账落终态后再死。宽限窗未退再 SIGKILL。
- **Windows**：本仓实测（两组旗标对照）：`CREATE_NO_WINDOW` 子进程有自
  己的隐形控制台，`CTRL_BREAK_EVENT` 从 UI 进程**送达不了**（发送成功返
  回、子进程纹丝不动）；即使共享控制台送达，Python 把 CTRL_BREAK 映射为
  SIGBREAK 直接终止、不产生 KeyboardInterrupt。所以 Windows 路径**如实
  是硬杀**——七个阶段全部 in-process 跑在编排器单进程里
  （`_default_runners` 逐个 `_load_script_main`），杀单进程即完备，无孤
  儿阶段。硬杀后状态工件停在 `running`：本页**不伪造终态**（状态工件只
  有编排器写），凭句柄证据（`poll()` 已退出）在取消结果区如实标注。

## Non-goals

- 不取消调度器的自动运行（不同进程属主，越权杀进程是另一类风险）。
- 不给编排器加协作式取消哨兵（那要改 `_execute_daily_update` 阶段语义，
  红线另议）。
- UI 重启后旧运行不可取消（句柄只活在会话内存）——如实降级，不是缺陷。
